# HTTP API

Everything the MCP tools do is also available over plain HTTP, for scripts, CI jobs and agents without MCP.

- **Auth:** every request (except `/healthz` and `/api/setup`) sends `Authorization: Bearer <credential>`. A credential is an agent key or personal key (`ls_…`), an account session token, or a static config token. With [Cloudflare Access sign-in](cloudflare-access.md) on, a request without one can instead come through Access, which adds a signed `Cf-Access-Jwt-Assertion`.
- **Projects:** every endpoint takes `?project=<id or key>`. It's needed only when your credential reaches several [projects](projects.md): writes then fail with `400 Say which project: …` without it, and listings cover every project you can see. Lane and group ids in paths and bodies are per project.
- **Escalation ids:** wherever a path or field takes an escalation id, its code works too, e.g. `A12` (case doesn't matter), or `SH-A12` to name the project. Plain numbers from before lane codes (`42`) still resolve.
- **Observer keys** are read-only: they may use the *any* routes below with `GET` only, and never pass `ack`. Anything else is `403`. See [Observer keys](accounts.md#observer-keys).
- **Errors:** responses are JSON. Errors look like `{"error": "…"}` with a 4xx status:
  - `400` validation (with `issues`)
  - `401` no or invalid credential
  - `403` wrong role (including any change from an observer key), or not a project admin
  - `404` not found
  - `409` a state conflict, such as deciding an already-decided escalation

## Example: an agent's whole loop

```bash
URL=https://lanesignal.example.com
KEY=ls_…

# register the group once per session, then publish lane state (creates the lane on first call)
curl -X PUT $URL/api/groups/payments-epic -H "authorization: Bearer $KEY" -H 'content-type: application/json' \
  -d '{"name":"Payments epic"}'
curl -X PUT $URL/api/lanes/auth-rework -H "authorization: Bearer $KEY" -H 'content-type: application/json' \
  -d '{"name":"Auth rework","group":"payments-epic","status":"pending_ci","ticket":"redmine:4812",
       "activity":"Waiting on CI for PR #311",
       "links":[{"label":"PR #311","url":"https://github.com/o/r/pull/311","kind":"pr"}]}'

# ask the owner (their phone is notified)
ID=$(curl -s -X POST $URL/api/escalations -H "authorization: Bearer $KEY" -H 'content-type: application/json' \
  -d '{"laneId":"auth-rework",
       "context":"legacy_role has had no reads for 90 days; rollback needs a backup restore.",
       "question":"Drop the legacy_role column?",
       "recommendation":"Drop it; the auth rework is simpler without it.",
       "cost":"A restore from backup if we were wrong.",
       "alternatives":["Rename it to legacy_role_deprecated for one release."],
       "acceptMeans":"Drop it in migration 0042","rejectMeans":"Keep it for one more release",
       "attachments":["<id from POST /api/attachments>"]}' | jq -r .id)

# wait for answers on any of the group's lanes (up to 24h per call; repeat while ready is false)
curl -s "$URL/api/wait?group=payments-epic&timeout=86400" -H "authorization: Bearer $KEY" | jq '.items[] | select(.kind == "decided") | {code,text}'

# acknowledge first: returns the final decision, and publishes the lane's next state
curl -s -X POST $URL/api/escalations/$ID/ack -H "authorization: Bearer $KEY" \
  -H 'content-type: application/json' -d '{"note":"dropping in migration 0042","status":"active","activity":"Dropping legacy_role"}'

# or, if the owner answered in the agent's session (and always with LANESIGNAL_DECISIONS=false):
# dismiss it, saying what was decided, and publish the next state
curl -s -X POST $URL/api/escalations/$ID/withdraw -H "authorization: Bearer $KEY" \
  -H 'content-type: application/json' -d '{"note":"Sam: drop it (in session)","status":"active","activity":"Dropping legacy_role"}'
```

So does anyone who could see a requirement a person moved into a project they can't see. The stream ends when memberships or projects change; reconnect and re-snapshot. | `POST /api/groups/:id/ack` | agent | `{upTo}`: acknowledge the group's messages up to that id (the last one handled). Never moves back, never past the latest. When the position moves, a `group` event carries the group's new `overseerReadId`. |

When the new one is pending, the old one stays in force with `supersededBy` set until the new one is approved (`409` if it already has a replacement waiting) |
| `PATCH /api/requirements/:id` | human | Fix `requirement` or `justification` wording. `403` for a personal key on a locked product's requirement |
| `POST /api/requirements/:id/approve` | human | `{scope?, products?, project?}`: a pending requirement becomes `active`, superseding the one it replaces, with the scope given (as for `PUT …/scope`) set in the same step (`409` if it isn't pending; `403` for a personal key) |
| `PUT /api/requirements/:id/scope` | human | `{scope, products?, project?}`: a person moves a pending or active requirement to global, project-wide or products. Same id and status (no re-approval); the change is logged (`…/changes`) and `needsRegrouping` clears. `project` moves it into another project (or out of global); a requirement citing an escalation can only move to that escalation's project or to global. Locks don't apply. `403` for a personal key |
| `GET /api/products?project=&archived=true` | any | Products requirements are scoped to, by name, with `locked` and `requirements` (how many in force). Archived ones only with `archived=true` |
| `POST /api/products?project=` | human | `{id, name, color?, parent?}`: a signed-in person adds a product (`id` kebab-case; `409` if taken, naming the product that holds it). `parent` puts it under a live top-level product, one level deep: `404` if there's no such product, `409` if it's a subproject or archived. Agents and personal keys can't (`403`) |
| `PATCH /api/products/:id?project=` | human | `{name?, color?, locked?, archived?, parent?}`. `parent` (a top-level product's id, or `null`) moves it: `400` under itself, `404` if there's no such product, `409` if it has subprojects, or the parent is itself a subproject or archived. Archiving is also `409` while it has live subprojects, and unarchiving while its parent is archived. A locked product refuses agents' and personal keys' records, supersedes and scope changes touching it. Archiving is `409` while requirements in force are scoped to it. `403` for a personal key |
| `POST /api/requirements/:id/reject` | human | `{reason}` (required, at most 2,000 characters): a pending requirement becomes `rejected`, with `rejectionReason` set. A requirement it was to replace stays in force with no replacement waiting. `409` if it isn't pending or has a replacement waiting (decide that first); `403` for a personal key |
| `POST /api/requirements/:id/retire` | human | An active requirement no longer applies; nothing replaces it. `409` while it has a replacement waiting, and for a pending one: reject it instead (app versions from before rejection reasons, which retired pending ones, get this error until updated) |
| `POST /api/requirements/:id/restore` | human | Undo a retire (it comes back `active`) or a rejection (it comes back `pending`, its reason cleared, and again the pending replacement of what it was to replace; `409` if that has changed since) |
| `POST /api/push/register`, `/unregister` | human | Used by the Android app |
| `POST /api/admin/people` | static human token | Break-glass: add a person `{email, name, password, admin?}` |
| `POST /api/admin/people/password` | static human token | Break-glass: `{email, password}`, which also signs them out |
| `/api/auth/*` | | Better Auth: sign-in, sign-out, password change, agent keys (`/api-key/*`), admin (`/admin/*`). The web app uses these |
| `POST /mcp` | any | MCP Streamable HTTP. See [agents](agents.md) |
